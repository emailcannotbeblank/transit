# 并发用例与工具盘点（重点：并发销毁沙箱）

## 1. 结论摘要

仓库内已经有多套并发工具，但没有一套现成工具完整满足“先批量创建并稳定运行，再用 barrier 同时发起 DELETE，只测销毁”的需求。

最接近的工具是：

- 外部端到端：`examples/cube-bench`；
- 直接压 CubeAPI：`CubeAPI/examples/benchmark.py`；
- 直接压 Cubelet 并读取销毁分段指标：`Cubelet ... cubebox multirun`；
- 直接压 CubeMaster：`CubeMaster ... cubebox multirun`，但销毁分段指标当前不会从 Cubelet 透传，且 `delcc` 标志创建后未实际使用。

## 2. 并发沙箱生命周期工具

### 2.1 `examples/cube-bench`（推荐作为外部基线）

位置：`examples/cube-bench/`

能力：

- Go 实现，直接调用 CubeAPI HTTP；
- `-c/--concurrency` 控制并发槽，`-n/--total` 控制总迭代数；
- 默认 `create-delete`，分别记录 CreateMs/DeleteMs；
- 输出 min/avg/std/P50/P95/P99/max、直方图、吞吐和 JSON；
- 支持 warmup、dry-run、非交互模式。

示例：

```bash
cd /home/zry/桌面/cubesandbox/CubeSandbox/examples/cube-bench
make
E2B_API_URL=http://127.0.0.1:3000 \
E2B_API_KEY=e2b_000000 \
CUBE_TEMPLATE_ID=<template-id> \
./bin/cube-bench -c 20 -n 200 --no-tui -o report.json
```

并发语义：每个 goroutine 在一个并发槽内先 CREATE，再立即 DELETE；槽直到 DELETE 完成才释放（`runner.go:27-106,132-147`）。因此 DELETE 最多有 `c` 个同时在飞，但会被各 CREATE 完成时间打散，不是严格同时起跑的纯销毁波次。

适用：用户真实端到端时延、回归测试、结果导出。

不适用：隔离 Cubelet、存储或网络阶段；预创建 N 个后瞬时并发删除。

### 2.2 `CubeAPI/examples/benchmark.py`

位置：`CubeAPI/examples/benchmark.py`

能力与 cube-bench 类似，使用 `httpx.AsyncClient`、`asyncio.Semaphore` 和 Rich TUI；JSON 包含每次 `delete_ms`。

并发语义同样是“一个 semaphore 槽内 CREATE→DELETE”（`benchmark.py:524-573`），所有任务通过 `asyncio.gather` 等待（`benchmark.py:639-704`）。

适用：快速改 Python 实验、可视化演示。

注意：与 cube-bench 功能重叠；不要把两套结果混为不同层级的测量。

### 2.3 `CubeAPI/examples/go/benchmark.go`

位置：`CubeAPI/examples/go/benchmark.go`

能力：固定数量 worker 循环 CREATE→Kill，记录 createMs 和 killMs，输出分位数；`--nodel` 可只创建不删除。

并发语义：每个 worker 内串行 create/kill，不同 worker 并行（`benchmark.go:50-79,181-199`）。也没有独立 delete-only phase。

### 2.4 CubeMaster CLI `cubebox multirun`

位置：`CubeMaster/cmd/cubemastercli/commands/cubebox/benchrun.go`

能力：

- 直接调用 CubeMaster `/cube/sandbox`；
- `runcc` 并发数、`runcnt` 循环数、`same` 严格同步每轮创建；
- 创建成功后发 `sync=true` Destroy；
- 记录总请求耗时和响应 `ext_info` 的各项分位数；
- 有同步重试和异步重试清理。

关键问题：

1. `delcc` 会创建 `delLimiter`（`benchrun.go:297-299`），但文件中没有 acquire/release 调用，因此当前标志对销毁并发没有实际作用。
2. CubeMaster 同步删除响应结构有 `ExtInfo` 字段，但 `callCubelet()` 没有把 Cubelet response 的 `ext_info` 复制进去。因此 CLI 的 `for k,v := range rsp.ExtInfo` 在正常同步路径拿不到节点分段数据。
3. 仍是每个 worker 创建后立即销毁，`same` 只对创建轮次做 barrier，不能保证 DELETE 同时起跑。

适用：压测 Master 调度/HTTP 路径、验证同步重试。

### 2.5 Cubelet CLI `cubebox multirun`（当前最佳节点级工具）

位置：`Cubelet/cmd/cubecli/commands/cubebox/benchrun.go`

能力：

- 直接 gRPC 调 Cubelet，绕开 CubeAPI/CubeMaster；
- `--addrm` 执行创建+销毁；
- `--runcc`、`--runcnt` 控制并发和轮次；
- `--same` 让同一轮创建同步起跑；
- `--delcc` 通过 semaphore 实际限制销毁并发（`benchrun.go:179-193,478-513`）；
- 直接读取 Cubelet Destroy response 的 `ext_info`，按 key 输出分位数。

示意：

```bash
cubecli cubebox multirun \
  --addrm --runcc 50 --runcnt 20 --delcc 50 --same \
  --printall <request.json>
```

适用：节点工作流吞吐、分段指标、排除上游噪声。

限制：依旧不是预创建后统一 DELETE；`delcc` 只是上限，不是 delete barrier；直接打 Cubelet 不能代表用户端总时延。

## 4. 服务端并发控制设施

### Cubelet workflow limiter

- 配置：`flows.destroy.concurrent = 100`；
- 实现：`TryAcquire()`；
- 行为：到达上限后立即返回并发错误，不排队；
- 指标：Prometheus `cube_cubebox_scheduler_realtime_destroy_num` 和 CLS `DeletionPeak`。

### Master 异步销毁队列

- `AsyncTaskQueueSize` 默认 10000；worker 默认 `runtime.NumCPU()`；
- scheduler 每 5 秒按健康节点数、Master 副本数和 `destroy_concurent_limit` 调整 Destroy handler 限流；
- 只影响 `sync=false` 内部异步路径，当前 CubeAPI 删除是 `sync=true`，不能靠它保护 Cubelet。

### 每沙箱生命周期锁

Cubelet 使用 keyed lock 让同一沙箱的 delete 与 pause/resume/rollback 互斥；不同 sandbox ID 不共享这把锁。高并发删除不同沙箱时，它不是全局瓶颈；删除与自动暂停竞态时，它会造成最多 2 秒等待或 503 重试。

## 5. 现有工具的核心缺口

1. 无纯 `delete-only` 模式：无法预创建 N 个运行态沙箱，再同时发 DELETE。
2. 无 delete barrier：创建结束时间会把 DELETE 请求摊散，低估突发销毁的竞争。
3. 外部工具看不到 Cubelet `ext_info`：难以自动关联端到端尾延迟和节点阶段。
4. 暂停沙箱与运行沙箱未分组：自动恢复成本会污染总体分布。
5. 未采集并发时的系统资源：缺少 CPU、iowait、磁盘 fsync、锁/阻塞、network-agent RPC 等伴随指标。
6. 没有明确的饱和点测试：应同时观察成功率、P99、吞吐和 `ConcurrentFailed`，而不是只比较平均值。

## 6. 建议的销毁基准用例

建议在现有 `examples/cube-bench` 增加独立模式，实验结构如下：

```text
prepare: 并发创建 N 个 -> 确认全部 RUNNING -> settle 2~5s
barrier: 所有 DELETE worker 就绪
measure: 同时释放 barrier，记录每请求 latency、wall time、错误码
verify: 列表/节点资源/Redis route/CubeCoW 对象均已收敛
```

至少覆盖：

- 并发：1、5、10、20、50、80、100、120；
- 状态：RUNNING、PAUSED；
- 沙箱形态：默认、带 plugin volume、带 lifecycle hooks、带多 container；
- 节点：单节点固定落点、多节点均衡；
- 数据：成功率、吞吐、P50/P95/P99/max、各阶段关键路径、CPU/iowait、workflow in-flight/peak。

只有这种用例才能回答“高并发销毁的性能上限在哪里、哪一步先饱和、优化后是否真的缩短尾延迟”。
