# CubeSandbox 日志文件说明

## 1. 文档范围

本文介绍严格并发销毁测试采集的以下七类日志：

1. CubeMaster 请求日志；
2. Cubelet 请求日志；
3. Cubelet 耗时统计日志；
4. CubeShim 请求事件日志；
5. CubeShim 耗时统计日志；
6. CubeVMM/Hypervisor 运行日志；
7. network-agent 请求日志。

本文以第一轮全量观测目录为例：

```text
/home/zry/桌面/0702/0725/raw/strict-barrier-n10/logs
```

第二轮全量观测的目录结构相同：

```text
/home/zry/桌面/0702/0725/raw/strict-barrier-n10-repeat/logs
```

## 2. 日志来源与采集方式

统一采集入口：

```text
/home/zry/桌面/0702/0725/tools/run_observability_example.sh
```

脚本在测试开始前使用 `stat -c %s` 记录每个宿主机日志文件的
byte offset。测试完成后再使用 `tail -c`，只截取本轮测试期间新增
的日志，写入 `raw/<run>/logs/`。

因此，`raw` 中的文件不是完整历史日志，而是对应测试运行的日志窗口。

| 采集文件 | 宿主机原始文件 |

| `Cubelet-Cubelet-stat.log` | `/data/log/Cubelet/Cubelet-stat.log` |
| `CubeShim-cube-shim-req.log` | `/data/log/CubeShim/cube-shim-req.log` |
| `CubeShim-cube-shim-stat.log` | `/data/log/CubeShim/cube-shim-stat.log` |

## 3. 日志对应的调用链

七类日志覆盖的主要调用链如下：

```text
客户端
  -> CubeAPI
  -> CubeMaster
  -> Cubelet
  -> containerd/CubeShim
  -> guest agent
  -> VMM/Hypervisor

Cubelet
  -> network-agent
```

同一请求通常可以使用以下标识关联：

- `RequestId`：关联 Master 与 Cubelet 请求；
- `InstanceId` 或 `sandbox_id`：关联整个 sandbox 生命周期；
- `ContainerId`：关联 Shim 中的 sandbox/container；
- 时间戳：确认跨组件事件的先后顺序。

## 4. CubeMaster 请求日志

### 4.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/CubeMaster-cubemaster-req.log

宿主机源文件：
/data/log/CubeMaster/cubemaster-req.log
```

### 4.2 格式

该文件使用 JSON Lines 格式，每一行是一个 JSON 对象。常见字段：

| 字段 | 含义 |
|---|---|
| `@timestamp` | 日志时间 |
| `Action` | HTTP 或业务动作，如 `GET`、`POST`、`DELETE` |
| `RequestId` | 请求 ID |
| `InstanceId` | sandbox ID |
| `Caller` | 调用方 |
| `Callee` | 被调用模块 |
| `CalleeAction` | 被调用动作或 HTTP 路径 |
| `RetCode` | 返回码 |
| `CodeLine` | 打印日志的源码位置 |
| `LogContent` | 具体请求、响应或内部事件 |

### 4.3 主要内容

该日志记录 CubeMaster 控制面请求和内部处理过程，包括：

- `/notify/health` 健康检查；
- `/cube/sandbox` 创建和销毁请求；
- `/cube/sandbox/list` 查询；
- 节点状态和调度指标；
- Redis 元数据读取和更新；
- Cubelet Destroy 返回值；
- CubeMaster 对客户端的最终响应。

销毁分析中最重要的记录形态：

```text
Action="DELETE"
LogContent="Destroy_rsp:{...}"
```

`Destroy_rsp` 内的 `ext_info` 包含 Cubelet 返回的阶段耗时，例如：

```text
cubebox
cubebox-service-unknown-container
storage
network
cgroup
volume
netfile
cube-sandbox-store
del-task-sandbox
del-sandbox-metadata
sandbox-del-container
```

其中部分值采用 Base64 编码。`analyze_destroy_logs.py` 会解码这些值，
再按 sandbox ID 写入 `destroy-breakdown.json/csv`。

### 4.4 适合分析的问题

- 客户端请求何时进入 CubeMaster；
- Master 是否成功调用 Cubelet；
- 单个 sandbox 的 Destroy 返回是否成功；
- Cubelet 返回的各销毁阶段耗时；
- Cubelet 完成后，Master/CubeAPI 还有多少收尾时间。

## 5. Cubelet 请求日志

### 5.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/Cubelet-Cubelet-req.log

宿主机源文件：
/data/log/Cubelet/Cubelet-req.log
```

### 5.2 格式

该文件也是 JSON Lines。常见字段与 CubeMaster 日志相似：

```text
@timestamp
Action
RequestId
InstanceId
Caller
Callee
CalleeAction
RetCode
LogContent
```

### 5.3 主要内容

该日志记录 Cubelet 接收的请求和工作流执行过程，包括：

- `RunCubeSandboxRequest` 完整创建请求；
- volume、container、image 和 resource 配置；
- annotation、label、模板 ID 和 benchmark run ID；
- sandbox 网络、端口和 probe 配置；
- `DestroyCubeSandboxRequest` 销毁请求；
- storage、network、runtime 等内部处理日志；
- Cubelet workflow 中的错误和状态信息。

典型销毁请求：

```text
Action="Destroy"
Callee="workflow"
CalleeAction="Destroy"
LogContent="DestroyCubeSandboxRequest: requestID:... sandboxID:..."
```

注意：该文件中的部分正常请求可能也带有 `LogLevel="ERROR"`。判断业务
是否失败时，应结合 `RetCode`、响应内容和对应 stat 日志，不能只看
`LogLevel`。

### 5.4 适合分析的问题

- Master 实际发送给 Cubelet 的请求内容；
- 创建或销毁是否携带了正确的模板、网络和存储配置；
- `RequestId` 与 `sandbox_id` 的对应关系；
- Cubelet 工作流在哪一步打印了异常；
- 请求是否真正进入 Cubelet。

当前 `analyze_destroy_logs.py` 不直接解析该文件；它主要用于人工核查
请求内容和执行顺序。

## 6. Cubelet 耗时统计日志

### 6.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/Cubelet-Cubelet-stat.log

宿主机源文件：
/data/log/Cubelet/Cubelet-stat.log
```

### 6.2 格式

该文件是结构化 JSON Lines，核心字段：

| 字段 | 含义 |
|---|---|
| `Action` | `Create` 或 `Destroy` |
| `Callee` | 被统计的阶段或模块 |
| `CalleeAction` | 阶段动作 |
| `CostTime` | 阶段耗时，单位为毫秒 |
| `InstanceId` | sandbox ID |
| `RequestId` | 请求 ID |
| `RetCode` | 阶段返回码 |
| `Caller` | 调用方 |

### 6.3 主要内容

创建阶段常见 `Callee`：

```text
storage
network
sandbox-create
sandbox-start
sandbox-probe
cubebox
cubebox-service
cubebox-service-inner
```

销毁阶段常见 `Callee`：

```text
cubebox
cubebox-service-unknown-container
del-task-sandbox
sandbox-del-container
```

另外还可能包含 `lifetimemetric` 的 CPU、内存和生命周期统计。

### 6.4 适合分析的问题

- Cubelet 整体 Create/Destroy 耗时；
- runtime/cubebox 是否为主要阶段；
- storage、network 等资源步骤耗时；
- 删除 task、container 和 metadata 的耗时；
- 不同 sandbox 之间的阶段差异。

`analyze_destroy_logs.py` 会读取：

```text
Action="Destroy"
Callee
CostTime
InstanceId
```

并将对应值写入逐 sandbox 拆解结果。

## 7. CubeShim 请求事件日志

### 7.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/CubeShim-cube-shim-req.log

宿主机源文件：
/data/log/CubeShim/cube-shim-req.log
```

### 7.2 格式

该文件使用 JSON Lines，字段相对精简：

| 字段 | 含义 |
|---|---|
| `Module` | 固定为 `Shim` |
| `InstanceId` | sandbox ID |
| `ContainerId` | container/sandbox ID |
| `Timestamp` | UTC 时间戳 |
| `LogContent` | Shim 事件或转发的 guest 日志 |
| `FunctionType` | 功能类型，当前记录中通常为空 |

### 7.3 主要内容

创建过程包括：

```text
create req start/finish
load spec finish
snapshot restore init
start vm start
agent is ready
start container finish
start sandbox finish
```

销毁过程包括：

```text
kill req start/finish
wait req start/finish
delete req start/finish
shutdown req start/finish
destroy sandbox start/finish
wait vm shutdown
wait ch exit
```

`LogContent` 中还可能嵌入 guest agent 的 JSON 日志，例如：

```text
signal process
signal all the remaining processes
wait process
receive destroy sandbox
```

### 7.4 阶段耗时计算

`analyze_destroy_logs.py` 按 `InstanceId` 分组并按 `Timestamp` 排序，
然后计算：

| 指标 | 计算公式 |
|---|---|
| `shim_kill_ms` | `kill req finish - kill req start` |
| `shim_wait_task_ms` | `wait req finish - wait req start` |
| `shim_delete_req_ms` | `delete req finish - delete req start` |
| `shim_shutdown_req_ms` | `shutdown req finish - shutdown req start` |
| `shim_destroy_sandbox_ms` | `destroy sandbox finish - destroy sandbox start` |
| `shim_guest_destroy_rpc_approx_ms` | `wait vm shutdown - destroy sandbox start` |
| `shim_wait_vm_shutdown_ms` | `wait ch exit - wait vm shutdown` |
| `shim_vmm_join_ms` | `destroy sandbox finish - wait ch exit` |

`guest Destroy RPC` 标记为估算值，因为该区间还可能包含 Shim 侧获取锁、
构造请求和日志开销。

### 7.5 适合分析的问题

- Kill、Wait、Delete、Shutdown 各自耗时；
- guest Destroy RPC 是否慢；
- 等待 `VmShutdown` event 是否慢；
- VMM `join()` 是否占据主要时间；
- 同一 sandbox 的 Shim 与 VMM 事件是否一致。

## 8. CubeShim 耗时统计日志

### 8.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/CubeShim-cube-shim-stat.log

宿主机源文件：
/data/log/CubeShim/cube-shim-stat.log
```

### 8.2 格式

该文件是结构化 JSON Lines。核心字段：

```text
Action
Caller
Callee
CalleeAction
CostTime
RetCode
InstanceId
ContainerId
```

### 8.3 主要内容

创建阶段包括：

```text
Ch / LaunchVmm
Ch / RestoreVm
Agent / CreateSandbox
Agent / CreateContainer
Agent / ResetVm
Shim / CreatePodSandbox
```

销毁阶段包括：

```text
Shim / DeleteContainer
```

它比 `cube-shim-req.log` 粒度更粗，但已经直接提供 `CostTime`。

### 8.4 适合分析的问题

- VMM launch/restore 的粗粒度耗时；
- guest agent 创建 sandbox/container 的耗时；
- Shim DeleteContainer 的统计耗时；
- req 日志时间差和 stat 日志统计是否一致。

`analyze_destroy_logs.py` 会读取：

```text
Action="Delete"
CostTime
InstanceId
```

并输出 `shim_delete_container_stat_ms`。

## 9. CubeVMM/Hypervisor 日志

### 9.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/CubeVmm-vmm.log

宿主机源文件：
/data/log/CubeVmm/vmm.log
```

### 9.2 格式

该文件是纯文本，不是 JSON Lines。典型结构：

```text
<sandbox-id> --- <数值字段> --- <level> --- <thread>
<Rust 源文件:行号> -- <日志内容>
```

每行开头的 sandbox ID 可以与 Shim 日志关联。日志中通常还包含线程名、
Rust 源码文件和行号。

### 9.3 主要内容

启动和恢复阶段：

```text
Cube-Hypervisor version
control_loop is ready
API request event: VmRestore
disk/net/vsock/pmem 配置
VCPU 和设备线程启动
```

销毁和退出阶段：

```text
ACPI Shutdown signalled
VM exit event
KILL_EVENT received, stopping epoll loop
vsock connection remove/reset
virtio disk、net、pmem、console、rng 等线程退出
```

### 9.4 适合分析的问题

- VM 是否收到 ACPI shutdown；
- `VM exit event` 何时出现；
- 哪些设备线程在退出；
- virtio、vsock、disk、TAP 等清理是否异常；
- Shim 的 `wait vm shutdown` 和 `wait ch exit` 期间，VMM 在做什么。

当前 `analyze_destroy_logs.py` 不直接解析 VMM 日志。报告中的
`wait VM shutdown` 和 `VMM join` 来自 Shim 打点；VMM 日志用于进一步
解释这两个区间内部发生的工作。

## 10. network-agent 请求日志

### 10.1 位置

```text
采集副本：
raw/strict-barrier-n10/logs/network-agent-network-agent-req.log

宿主机源文件：
/data/log/network-agent/network-agent-req.log
```

### 10.2 格式

该文件使用 JSON Lines。常见字段：

```text
@timestamp
Module
LogLevel
RetCode
LocalIp
Version
LogContent
```

该文件中的结构化 `InstanceId` 字段可能为空，真实 sandbox ID 经常直接
写在 `LogContent` 的 `sandbox_id=...` 中。

### 10.3 主要内容

创建阶段：

```text
EnsureNetwork request
tap dequeued from pool
register cubevs tap
sandbox IP、gateway、route、ARP 和 port mapping
```

销毁阶段：

```text
staging tap for pool
tap pooled
```

第一轮 N=10 日志中包含：

- 10 次 `EnsureNetwork`；
- 10 次 TAP 出池；
- 10 次 cubevs TAP 注册；
- 10 次 TAP 回收准备；
- 10 次 TAP 重新入池。

### 10.4 适合分析的问题

- sandbox 是否成功分配网络；
- sandbox ID 对应哪个 TAP 和 IP；
- 销毁后 TAP 是否回到池中；
- network-agent allocation 是否残留；
- 网络失败发生在申请、注册还是回收阶段。

TAP 接口在销毁后仍存在不一定表示泄漏。当前实现使用预分配池复用 TAP，
应重点检查 allocation/state 是否释放以及 TAP 是否回到池中。

当前 `analyze_destroy_logs.py` 不直接解析该文件。Cubelet/Master 返回的
`network` 阶段耗时用于汇总，network-agent 日志用于验证网络行为和残留。

## 11. 分析脚本使用关系

销毁拆解脚本：

```text
/home/zry/桌面/0702/0725/tools/analyze_destroy_logs.py
```

| 日志 | 是否直接用于 `destroy-breakdown` | 读取内容 |
|---|---|---|
| CubeMaster req | 是 | `Destroy_rsp.ext_info` |
| Cubelet req | 否 | 人工核查请求与流程 |
| Cubelet stat | 是 | `Action=Destroy`、`Callee`、`CostTime` |
| CubeShim req | 是 | `Timestamp` 和阶段事件 |
| CubeShim stat | 是 | `Action=Delete`、`CostTime` |
| CubeVMM | 否 | VM/设备线程退出分析 |
| network-agent | 否 | 网络分配、回收和残留分析 |

## 12. 常用查看命令

按 sandbox ID 查看跨组件日志：

```bash
sandbox_id=<sandbox-id>
rg "$sandbox_id" raw/strict-barrier-n10/logs
```

查看 Master 销毁响应：

```bash
jq -c '
  select(
    .Action == "DELETE"
    and (.LogContent | startswith("Destroy_rsp:"))
  )
' raw/strict-barrier-n10/logs/CubeMaster-cubemaster-req.log
```

查看 Cubelet 销毁阶段耗时：

```bash
jq -c '
  select(.Action == "Destroy")
  | {
      timestamp: .["@timestamp"],
      sandbox_id: .InstanceId,
      stage: .Callee,
      cost_ms: .CostTime,
      ret_code: .RetCode
    }
' raw/strict-barrier-n10/logs/Cubelet-Cubelet-stat.log
```

查看 Shim 销毁时间线：

```bash
jq -c '
  select(
    .LogContent
    | test(
        "^(kill req|wait req|delete req|shutdown req|"
        + "destroy sandbox|wait vm shutdown|wait ch exit)"
      )
  )
  | {
      timestamp: .Timestamp,
      sandbox_id: .InstanceId,
      event: .LogContent
    }
' raw/strict-barrier-n10/logs/CubeShim-cube-shim-req.log
```

查看 VMM 销毁相关事件：

```bash
rg -i \
  'shutdown|VM exit event|KILL_EVENT|vsock remove' \
  raw/strict-barrier-n10/logs/CubeVmm-vmm.log
```

查看网络分配和回收：

```bash
rg \
  'EnsureNetwork|dequeued from pool|register cubevs tap|staging tap|tap pooled' \
  raw/strict-barrier-n10/logs/network-agent-network-agent-req.log
```
