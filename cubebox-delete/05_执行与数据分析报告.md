## 3. 新增严格生命周期用例

入口：`tools/lifecycle_destroy_case.py`

用例语义：

```text
健康检查
  -> N 个 CREATE worker 同一 barrier 起跑
  -> 等待全部 CREATE 返回
  -> settle 1 秒
  -> N 个 DELETE worker 同一 barrier 起跑
  -> 记录每请求起止时间、时延、wall time、启动偏斜
  -> SDK list 验证不存在用例创建的 sandbox ID
  -> 失败时 best-effort 清理
```

它补上了已有工具的两个缺口：

- DELETE 前已完成全部 CREATE，不会被各 worker 的 CREATE 完成时间打散；
- DELETE 有独立 barrier，不是仅设置最大并发数。

每个样本保留 `sandbox_id`、UTC 时间戳、epoch ns、latency 和错误，后处理可以按 sandbox ID 对齐 Master、Cubelet、Shim 日志。

## 5. 销毁关键路径拆解

下表比较两轮有组件日志的严格用例，字段为每轮 10 个样本的 mean：

| 阶段 | 20 ms 采样轮 | 100 ms 采样轮 | 解释 |
|---|---:|---:|---|
| 客户端 DELETE E2E | 102.580 | 126.907 | 用户体验口径 |
| Cubelet service | 95.441 | 118.836 | 节点销毁服务 |
| Master/API tail 估算 | 7.139 | 8.071 | `E2E - Cubelet service` |
| `runtime_cubebox` | 93.399 | 114.711 | container/task/Shim/VM |
| 资源阶段关键路径 | 1.100 | 3.358 | 并行 action 的最大值 |
| storage | 0.800 | 2.644 | CubeCoW/default storage |
| network | 0.800 | 3.058 | network-agent release |
| cgroup | 0.100 | 0.300 | pool/store |
| cleanup | 0.000 | 0.000 | 毫秒整数精度 |

workflow step 2 的 storage、network、cgroup、volume、netfile 和 sandbox store 是并行执行，必须取 `max(action)` 估算阶段耗时，不能求和。

结论：

1. 两轮中 `runtime_cubebox / E2E` 都约为 90%，运行时是稳定的主导项。
2. storage 与 network 均处于个位数毫秒，没有在 N=10 下形成主要尾延迟。
3. Master/API 同步收尾约 7–8 ms，不是主导项，但后续做极限优化时仍值得单独补 Redis/DB hook 指标。

`wait VM shutdown + VMM join` 基本解释了 shutdown 阶段；guest RPC 很小。下一步优化调查应优先围绕：

- VmShutdown event 到达时间；
- VMM 退出前的设备/线程清理；
- join 前后的固定等待或串行点；
- Kill/Wait 和 Shutdown 是否存在可消除的重复工作。

这些是当前数据支持的方向。仅凭源码里 CubeCoW 的全局锁，不能断言 storage 是本轮瓶颈。

## 10. 额外发现与清理

调试 Cubelet CLI request 时，错误地使用了 Master 风格的 `size_limit`。Cubelet CLI 通过 Go `encoding/json` 直接解析生成的 protobuf struct，该字段实际要求 `SizeLimit`。错误请求在 storage 校验失败前已经分配网络，留下了两个 network-agent state 文件。

处理结果：

- request 已修正为 `SizeLimit`；
- 对两个失败测试 ID 执行幂等 Cubelet Destroy；
- 因失败对象已没有 Cubelet cubebox metadata，Destroy 无法触发 network action；
- 最后通过 network-agent 的幂等 `ReleaseNetwork` 清除了两个 allocation；
- 最终 network-agent state 文件数为 0。

这提示存在一个值得单独提报的失败创建回滚场景：下游 storage 校验失败时，网络 allocation 可能残留。它不影响本报告中成功销毁样本的结论，但应该增加失败注入回归。

清理证据：`raw/cleanup/`

## 11. 当前无法直接采集的数据

以下不是漏采，而是当前代码或部署没有可用指标：

- CubeCoW `delete_volume` 的锁等待、unlink、fsync 时延；
- Shim DestroySandbox/guest/wait/join 的统一 duration metric，本报告由同 sandbox ID 的阶段日志时间差估算；
- Master 各 after-destroy hook 的独立时延；
- 成功且小于 5 ms 的 CubeLog trace 会被 `reportTrace()` 过滤；
- `tracecost` 在仓库中存在但未接线；
- CubeMaster 本机没有监听 pprof debug 端口，本次只采集了 Cubelet pprof；
- Rust Shim/CubeCoW 的 perf/strace 需要额外权限且会增加侵入性，本次未启用。

## 12. 建议的下一轮

在修改代码前，先建立稳定容量曲线：

1. 并发档位 1、5、10、20、50、80、100、120；
2. 每档至少 5～10 轮，分别记录 RUNNING 与 PAUSED；
3. 固定单节点和模板，Prom 采样 100～500 ms；
4. 同时保留严格 E2E、Cubelet ext_info、Shim 分段、错误率和残留检查；
5. 若 `runtime_cubebox` 持续占主导，先补 Shim duration 埋点；只有 storage 随并发明显上升时，再补 CubeCoW lock/fsync 埋点。

本轮 N=10 的数据已经足以把第一调查方向收敛到 Shim/VM 退出链路，但不足以给出系统饱和点。
