# 沙箱销毁耗时拆解工具与可观测性

## 1. 当前能拆到什么粒度

| 层级 | 现有工具/数据 | 能看到 | 主要缺口 |
|---|---|---|---|
| 客户端端到端 | cube-bench、CubeAPI benchmark | DELETE 总时延、分位数、成功率 | 不知道慢在 Master、Cubelet 还是 hook。 |
| CubeMaster | CubeLog request/Redis trace、pprof | Master 总体调用、Redis DEL 单次耗时、CPU/锁/阻塞 | 同步响应未透传 Cubelet ext_info；缺少明确的 post-hook 分段。 |
| Cubelet service/workflow | Destroy response `ext_info`、Cubelet-stat.log | workflow action、container task、metadata、pre/poststop 等毫秒耗时 | 只在直连 Cubelet 时容易消费；部分阶段未单独埋点。 |
| CubeShim | `StatDefer`、结构化 req/stat 日志 | DeleteContainer 耗时、destroy sandbox 的阶段日志 | 没有 DestroySandbox/Shutdown/VM join 的统一 duration 指标。 |
| CubeCoW | 日志、GetStorageMetrics | 对象数量/容量，删除事件 | 没有 delete_volume latency/锁等待/fsync latency。 |
| 系统级 | Cubelet/Master pprof、Prometheus | Go CPU、heap、goroutine/block/mutex；in-flight destroy | Rust Shim/CoW 锁与 syscall 仍需 perf/strace 等外部工具。 |

## 2. 端到端工具

### cube-bench

`examples/cube-bench` 记录 HTTP DELETE 从发出到响应体关闭前的时间，JSON 中保留每次 `delete_ms`。这是用户体验指标，必须保留为最终验收口径。

建议关注：

- P50/P95/P99/max，而非只看平均值；
- 成功率和 HTTP 408/409/503；
- delete throughput 与整轮 wall time；
- 同一并发下多轮结果和方差。

注意：当前 create-delete 模式不是严格的并发删除波次，见 `02_并发用例与工具.md`。

## 3. Cubelet Destroy `ext_info`（最有价值的现成分段数据）

Cubelet 在 `DestroyContext` 中累积分段 Metric，并在响应前写入 `DestroyCubeSandboxResponse.ExtInfo`（`Cubelet/services/cubebox/service.go:537-551,714-746`）。工作流中的每个 action 都自动记录耗时（`Cubelet/plugins/workflow/engine.go:435-495`）。

可能出现的 key 包括：

| key/模式 | 含义 |
|---|---|
| `cubebox-service-unknown-container` | Cubelet Destroy service 总耗时附近的指标。 |
| `cubebox` | 第一阶段节点运行时清理总耗时。 |
| `storage` | storage 插件总耗时。 |
| `network` | network-agent ReleaseNetwork + allocation 删除。 |
| `cgroup` | cgroup 归还和本地 DB 删除。 |
| `volume` | legacy volume lifetime 清理。 |
| `netfile` | netfile 目录删除。 |
| `cube-sandbox-store` | containerd sandbox store 删除。 |
| `cleanup` | 最后一阶段 GC 元数据清理。 |
| `del-task-sandbox` / `del-task-container-*` | containerd Task Kill/Wait/Delete 路径。 |
| `del-sandbox-metadata` / `del-container-*-metadata` | container metadata 删除。 |
| `sandbox-del-container` / `container-*-del-container` | 单个 container 的完整 destroyContainer。 |
| `sandbox-prestop` / `sandbox-poststop` | lifecycle HTTP hooks。 |
| `cube-storage-db-unknown-container` | storage 元数据读取部分。 |
| `cubebox-inner` | `cubebox - shim-like nested metrics` 的派生值。 |
| `cubebox-service-inner` | service 总耗时减 prestop 的派生值。 |
| `workflow-limiter` | limiter acquisition 尝试耗时；由于 TryAcquire，通常很小。 |

直接消费这些数据的现成工具是 Cubelet CLI `cubebox multirun --addrm --printall`，它会为每个 key 建 histogram 并输出分位数（`Cubelet/cmd/cubecli/commands/cubebox/benchrun.go:478-589`）。

### 解读注意事项

1. workflow 第二阶段插件是并行的，总耗时应近似该阶段最大 action 耗时，不应把 storage/network/cgroup 等相加。
2. 多 container 指标带 sandbox/container 索引；同名 key 写入 map 时最后值覆盖，原始 metric trace 比 response map 更完整。
3. 指标以毫秒整数写入，亚毫秒阶段会变为 0。
4. `reportTrace()` 为减少日志量会跳过成功且小于 5ms 的 metric（`service.go:451-465`），response ext_info 不受这个过滤影响。

## 4. 当前 ext_info 透传断点

这是最需要先修复的观测问题：

- Cubelet response 已包含 `map[string][]byte` 的 `ExtInfo`；
- CubeMaster 的 `DeleteCubeSandboxRes` 也定义了 `ExtInfo map[string]string`；
- 但同步 `callCubelet()` 只消费 volume ref event，没有把其余 `rsp.ExtInfo` 复制到 Master response（`CubeMaster/pkg/service/sandbox/sandbox_remove.go:180-216`）；
- CubeAPI 最终返回 204，也不会向外暴露调试字段。

因此当前分层做法应是：

- 外部用 cube-bench 测总时延；
- 同时按 requestID/sandboxID 从 Cubelet-stat.log 取分段；或
- 直接用 Cubelet CLI 做节点级对照实验。

若要自动化关联，优先在内部 benchmark/debug 路径透传 ext_info，而不是改变 E2B 兼容的 204 公共响应契约。

## 5. CubeLog trace/stat 日志

CubeLog `RequestTrace` 有 RequestID、InstanceID、Callee、CalleeAction、Cost、RetCode 等字段（`cubelog/metric.go:22-55`），启用后输出 `CostTime`（毫秒）。

重要日志位置：

| 文件 | 用途 |
|---|---|
| `/data/log/CubeMaster/cubemaster-req.log` | Master 请求与销毁结果。 |
| `/data/log/Cubelet/Cubelet-req.log` | Cubelet 工作流/插件详细日志。 |
| `/data/log/Cubelet/Cubelet-stat.log` | Cubelet 分段 metric trace。 |
| `/data/log/CubeShim/cube-shim-req.log` | Kill/Delete/Shutdown、guest agent、VM shutdown/join 阶段日志。 |
| `/data/log/CubeShim/cube-shim-stat.log` | Shim `StatDefer` 统计。 |
| `/data/log/CubeVmm/vmm.log` | Hypervisor 退出/设备释放。 |
| `/data/log/network-agent/network-agent-req.log` | ReleaseNetwork 细节。 |
| `/data/log/cubecow/cubecow.log` | reflink volume delete 事件。 |

路径依据：`docs/zh/guide/troubleshooting/component-log-locations.md:42-58`。

使用同一个 `RequestID` 和 `sandboxID` 关联日志。高并发实验不应只依赖时间戳，因为多个销毁会交错。

### Master Redis trace

Master 的 proxy key 删除会单独发出 `Callee=Redis, Action=Delete, CalleeAction=DEL` trace（`CubeMaster/pkg/localcache/redis_cache.go:580-606`）。这可以分离 Redis DEL，但生命周期 hook 内的 HDEL/XADD 和模板 DB hook 尚无同等统一分段。

## 6. CubeShim `StatDefer` 与阶段日志

`StatDefer` 在 Drop 时记录 duration ms（`CubeShim/shim/src/log/stat_defer.rs:55-115`）。当前删除路径明确埋点的是 Task `DeleteContainer`（`CubeShim/shim/src/service/task_srv.rs:279-351`）。

`destroy_sandbox()` 本身只有阶段日志：

- `destroy sandbox start`；
- guest agent Destroy RPC（timeout 200ms）；
- `wait vm shutdown`（单次最长 1000ms）；
- `wait ch exit`；
- `destroy sandbox finish`。

代码位置：`CubeShim/shim/src/sandbox/sb.rs:646-713`。

可先用相同 sandbox ID 的日志时间差粗拆，但推荐补充统一的 `StatDefer`：guest RPC、wait shutdown、join VMM、shutdown 总耗时。否则高并发下无法可靠计算每段分位数。

## 7. Prometheus/CLS 并发指标

Cubelet 暴露：

- `cube_cubebox_scheduler_realtime_destroy_num`：当前 in-flight destroy；
- `DeletionPeak`：采样周期内峰值。

实现见 `Cubelet/plugins/cube/internals/metric/collector.go:23-63,142-147` 和 `Cubelet/plugins/workflow/metric.go:87-101`。Prometheus 位于 Cubelet HTTP `/v1/metrics`（默认 `:9998`）。

这些是并发度指标，不是 latency histogram。建议在压测时间轴上同时采集，用于确认请求是否真的形成目标并发、是否触及 100 上限。

## 8. pprof

CubeMaster 和 Cubelet 都有 Go pprof：

- Cubelet 默认 debug port `:9966`，路径 `/debug/pprof/*`；
- CubeMaster 在配置了 debug address 后提供 `/debug/pprof/profile`、`trace`、heap/goroutine 等。

建议高并发销毁时采集：

```bash
curl -o cpu.pprof 'http://127.0.0.1:9966/debug/pprof/profile?seconds=30'
curl -o trace.out 'http://127.0.0.1:9966/debug/pprof/trace?seconds=10'
curl -o goroutine.txt 'http://127.0.0.1:9966/debug/pprof/goroutine?debug=2'
curl -o mutex.pprof 'http://127.0.0.1:9966/debug/pprof/mutex'
curl -o block.pprof 'http://127.0.0.1:9966/debug/pprof/block'
```

pprof 适合确认：workflow goroutine 堆积、Bolt/store 锁等待、network RPC 阻塞、GC/日志开销。端口必须仅在本机可达。

## 9. CubeCoW 指标和限制

CubeCoW 的 `GetMetrics` 提供 volume_count、snapshot_count、total_bytes、used_bytes（`cubecow/src/pkg/metrics/mod.rs:19-27`），适合验证销毁后对象数量和空间是否收敛。

但其删除实现中，全局 `name_index.write()` 覆盖 unlink、目录删除和 fsync（`cubecow/src/engine/reflink.rs:421-488`），当前没有：

- write-lock wait duration；
- unlink duration；
- fsync duration；
- delete_volume success/error counter/latency histogram。

这些正是高并发销毁最值得新增的埋点。

## 10. `tracecost` 工具

`Cubelet/pkg/tracecost/trace.go` 提供按 step 插入时间点并输出相邻/累计耗时的 `TimeCost`，但全仓库没有实际调用 `NewTimeCost/RecordStepInfo`，目前属于“存在但未接线”的工具，不能直接用于生产销毁拆解。

建议优先扩展已有 workflow Metric/StatDefer，而不是再引入一套平行埋点格式。

## 11. 推荐的测量组合

一次有效的优化实验应同时收集：

1. cube-bench：用户端 DELETE P50/P95/P99、吞吐、错误率；
2. Cubelet ext_info/Cubelet-stat：cubebox、storage、network、cleanup 及 nested container 指标；
3. Prometheus：realtime_destroy_num、节点 CPU/内存、MVM 数；
4. pprof：CPU、goroutine、mutex/block；
5. iostat/pidstat/perf（仓库外系统工具）：iowait、fsync、syscall、Rust 进程 CPU；
6. CubeShim/CubeCoW/network-agent 日志：按 requestID/sandboxID 定位长尾样本；
7. 销毁后一致性检查：Redis route、Cubelet list、CubeCoW volume_count、TAP/cgroup/进程均收敛。

先建立这套分层证据，再改并发模型或清理顺序，才能避免“总时延变快但资源异步泄漏/尾延迟恶化”的假优化。
