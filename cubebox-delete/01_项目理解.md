## 2. 项目定位

CubeSandbox 是面向 AI Agent 的硬件隔离沙箱系统。一个沙箱不是普通 Docker 容器，而是由 KVM/RustVMM 驱动的 MicroVM。项目强调：

- E2B SDK 兼容的外部 API；
- MicroVM 级硬件隔离；
- 预快照恢复带来的毫秒级启动；
- 单节点高密度和集群横向扩展；
- CubeCoW（XFS reflink）提供 rootfs、内存卷、快照和克隆；
- CubeVS/network-agent 提供节点侧网络生命周期管理。

总体架构说明见 `docs/zh/architecture/overview.md:1`。

## 3. 与销毁相关的组件

| 层级 | 组件 | 语言 | 销毁阶段职责 |
|---|---|---|---|
| 外部入口 | CubeAPI | Rust/Axum | 接收 `DELETE /sandboxes/{id}`，转成 CubeMaster HTTP 请求；对外删除固定为同步语义。 |
| 集群控制面 | CubeMaster | Go | 解析沙箱 ID、定位节点、调用 Cubelet、删除 Redis 路由、清本地缓存、执行生命周期/模板引用 hook。 |
| 节点控制面 | Cubelet | Go | 串行/并行编排运行时、存储、网络、cgroup、卷、元数据等清理；产生分段指标。 |
| 容器运行时桥接 | CubeShim | Rust | 实现 containerd Shim v2 的 Kill/Wait/Delete/Shutdown，通知 guest agent 退出并等待 VMM 结束。 |
| Guest | cube-agent | Rust | 收到 `DestroySandbox` 后通过 oneshot channel 触发 guest agent 主流程退出。 |
| 虚拟机 | CubeHypervisor | RustVMM/KVM | 处理 VM shutdown/delete 事件，释放 MicroVM 资源。 |
| 存储 | CubeCoW | Rust | 删除沙箱 rootfs/内存/default-medium reflink 卷及相关目录元数据。 |
| 网络 | network-agent / CubeVS | Go/eBPF | 同步释放沙箱网络、TAP、策略与持久化分配信息。 |
| 生命周期旁路 | cube-lifecycle-manager + Redis | Go | 消费 Master 发布的删除事件，清除自动暂停/恢复侧的视图。 |

## 4. 控制面和数据面的销毁边界

```text
E2B Client
  -> CubeAPI (同步 DELETE)
  -> CubeMaster (节点定位、RPC、集群元数据收尾)
  -> Cubelet (节点内销毁工作流)
       -> containerd -> CubeShim -> guest agent / Hypervisor
       -> storage / CubeCoW
       -> network-agent / CubeVS
       -> cgroup / volume / netfile / local stores
  <- Cubelet 完成
  -> CubeMaster 删除 Redis proxy key、本地 cache、DB/Redis hooks
  <- CubeAPI 返回 204
```

这个边界很重要：外部 DELETE 耗时不只等于“VM 退出耗时”，还包括 CubeAPI/Master 转发、节点所有资源清理以及 Master 的同步收尾。

## 5. 对外删除是同步语义

CubeAPI 的 `kill_sandbox()` 构造 `DeleteSandboxRequest` 时固定设置 `sync: Some(true)`（`CubeAPI/src/services/sandboxes.rs:293-301`）。随后 CubeMaster 在 `DestroySandbox()` 的同步分支直接调用 Cubelet（`CubeMaster/pkg/service/sandbox/sandbox_remove.go:102-114`）。

因此：

- SDK 的 `Sandbox.kill()` / HTTP DELETE 返回时，正常情况下节点销毁和 Master 收尾已经完成；
- CubeAPI 标准路由超时是 30 秒（`CubeAPI/src/routes.rs:26-32`）；
- CubeMaster 到 Cubelet 的通用 RPC 超时配置默认为 30 秒（`CubeMaster/conf.yaml:19-29`）；
- Cubelet 自身配置的 `destroy_dead_line` 是 60 秒（`Cubelet/config/config.toml:140-142`），但继承上游更早的 30 秒 deadline 时，实际仍受 30 秒限制。

CubeMaster 也支持 `sync=false` 的内部异步销毁队列，但这不是当前 E2B 外部 DELETE 的主路径。

## 6. Cubelet 销毁工作流模型

工作流由配置声明，而不是硬编码在一个函数里。默认配置见 `Cubelet/config/config.toml:153-164`：

```toml
[flows.destroy]
concurrent = 100
actions = [
  ["cubebox"],
  ["images", "storage", "cgroup", "network", "volume", "netfile", "cube-sandbox-store"],
  ["cleanup"]
]
```

含义：

1. 先独占执行 `cubebox`：停止容器任务、经 Shim 结束 VM、删除 containerd container、清 rootfs/fifo/runc 文件；
2. 再并行执行节点资源插件：storage、network、cgroup、volume、netfile、sandbox store 等；
3. 最后执行 cleanup 元数据清理。

同一步内用 `errgroup` 并行，不同步骤严格串行（`Cubelet/plugins/workflow/engine.go:374-409,435-495`）。销毁工作流并发上限为 100，使用 `TryAcquire`，超限会立即返回 `ConcurrentFailed`，不会在 Cubelet 内排队（`engine.go:357-372`）。

## 7. 主要状态位置

| 状态 | 位置/实现 | 销毁动作 |
|---|---|---|
| CubeAPI | 无状态 | 仅转发并映射错误。 |
| Master 沙箱/代理映射 | Redis + Master 本地缓存 | Cubelet 成功后同步 `DEL` proxy key，并删除本地 cache。 |
| 生命周期元数据 | Redis Hash + Stream | hook 同步执行 HDEL，再 XADD delete 事件。 |
| 模板/快照运行时引用 | MySQL/PostgreSQL（GORM） | destroy hook 释放 snapshot runtime ref，并删除 sandbox spec。 |
| Cubelet 沙箱对象 | 节点本地 store | 设置删除标记、更新状态，完成后删除对象。 |
| containerd metadata | 本地 Bolt/metadata plugin | Kill/Wait/Delete task 和 container metadata/snapshot cleanup。 |
| CubeCoW | XFS reflink 文件 + 内存索引 | unlink 卷文件、目录 fsync、更新全局 name index。 |
| 网络 | network-agent 持久化状态 | `ReleaseNetwork` 后删除 allocation store。 |

## 8. 与高并发销毁直接相关的配置

| 配置 | 默认/仓库示例 | 作用 |
|---|---:|---|
| Cubelet workflow `flows.destroy.concurrent` | 100 | 单 Cubelet 同时进入销毁工作流的最大请求数；超限立即失败。 |
| Master `destroy_concurent_limit` | 默认 50；`conf.yaml` 示例 100 | Master **异步**销毁任务的动态并发上限；不限制当前 `sync=true` 外部路径。 |
| Master `common_timeout_insec` | 30s | Master→Cubelet Destroy RPC deadline。 |
| CubeAPI route timeout | 30s | 外部 DELETE 总预算。 |
| Cubelet `destroy_dead_line` | 60s | 节点销毁内部预算，但不能延长父 context。 |
| Cubelet lifecycle lock wait | 最多 2s | 同一沙箱与 pause/resume/rollback 冲突时的锁等待上限。 |

## 10. 对优化工作的直接结论

1. 必须把“外部总时延”“Cubelet 工作流时延”“VM/容器时延”“节点资源并行清理时延”“Master 收尾时延”分开测量。
2. 外部同步路径绕过 Master 异步销毁限流；高并发的第一道实际节点门槛是 Cubelet workflow 的 100 并发 `TryAcquire`。
3. 销毁阶段已有并行设计，但第一阶段运行时清理和第三阶段 cleanup 严格串行；第二阶段总耗时取各并行插件的关键路径，而不是各耗时之和。
4. 运行中沙箱和暂停沙箱必须分开测试。暂停沙箱删除会先自动恢复，最多占用 5 秒预算，行为和瓶颈完全不同。
5. 当前项目的创建性能文档较完整，销毁性能还没有同等级的基准报告和纯销毁测试方法。
