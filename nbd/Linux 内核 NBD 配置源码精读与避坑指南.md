# Linux 内核 NBD 配置源码精读与避坑指南

本文档记录了在阅读 Linux 内核 NBD (Network Block Device) Netlink 消息处理代码（主要涉及 `nbd_genl_connect` 等函数）时，常见的源码疑惑与底层原理解析。

---

## 1. Netlink “套娃”解析与局部数组之谜

### ❓ 疑惑 1：`attr` 是什么？为什么在 `nla_for_each_nested` 循环里，每次都要重新定义一个 `socks` 数组？
* **背景**：代码中出现了 `struct nlattr *socks[NBD_SOCK_MAX+1];` 定义在循环内部。
* **解析**：
    1.  **`attr` 是什么**：它是内核从用户态收到的一长串 Netlink 消息（TLV 格式）中的**当前正在处理的子包裹（嵌套属性）**。
    2.  **防止“串味”**：放在循环内是为了保证每次解析新的 Socket 配置时，使用的都是一块干净的、未被污染的局部变量，防止上一个 Socket 的脏数据影响当前解析。
    3.  **零性能开销**：在 C 语言中，局部数组分配在**栈（Stack）**上。编译器会在函数入口一次性预留好内存，循环内部只是复用内存地址，没有动态分配（如 `malloc`）的性能开销。

### ❓ 疑惑 2：既然只想提取 `fd`，为什么搞一个指针数组，而不是只用一个 `sock` 指针？
* **解析**：
    * `attr` 本身依然是一个容器（套娃），里面包含该 Socket 的多个子属性（如 FD、State、Protocol 等）。
    * `socks` 数组本质上是一个**以属性类型 ID 为索引的“哈希表/字典”**。
    * 内核的 `nla_parse_nested_deprecated` 函数负责遍历 `attr` 的所有内容，并根据 ID 归类放到 `socks` 数组对应的格子里。这样后续只需 `socks[NBD_SOCK_FD]` 就能以 $O(1)$ 速度精准拿到目标数据。

### ❓ 疑惑 3：既然只用 `FD`，为什么要把整个包裹的属性都解析一遍？
* **解析**：
    1.  **TLV 格式限制**：数据在内存中是连续的 `[类型][长度][值]`，无法跳跃读取，想找 `FD` 就必须按顺序读取路过的每一个属性。
    2.  **安全校验**：内核不信任用户态数据。解析的过程也是根据 `nbd_sock_policy` 进行全面安全体检的过程。只要有一个多余属性格式非法，直接拒绝整个包裹，防止缓冲区溢出。
    3.  **API 通用性**：调用的是内核通用的“拆包裹”函数，函数本身不关心业务逻辑，只负责全量拆解。

## 2. 错误处理机制与 Sysfs 魔法

### ❓ 疑惑 4：`device_create_file` 失败后，为什么还要调用 `disk_to_dev`，而不是重试创建？
* **代码**：`dev_err(disk_to_dev(nbd->disk), "failed...\n");`
* **解析**：
    * 失败后再次调用 `disk_to_dev` 不是为了重试，而是为了**配合 `dev_err` 打印带有特定设备前缀（如 `nbd0:`）的错误日志**。
    * 内核采用**防御性编程**：创建文件失败通常意味着严重的系统异常（如 OOM 或命名冲突），强行重试毫无意义且危险。最安全的做法是记录日志后，立刻 `goto out` 安全回滚。

### ❓ 疑惑 5：`NBD_RT_HAS_BACKEND_FILE` 标志位里的“后端文件”到底是个啥文件？
* **解析**：
    * 它**不是**真实的磁盘镜像文件（如 `.qcow2` 或 `.img`）。
    * 它是内核在 `/sys/block/nbdX/` 目录下创建的一个名为 `backend` 的**虚拟纯文本文件 (sysfs file)**。
    * **作用**：为了系统的可观测性。管理员 `cat` 这个文件就能看到 NBD 连的是哪个 IP。设置这个标志位（Flag），是为了告诉内核：“设备销毁时，记得把这个虚拟文件删掉”。即使没有这个文件，也不影响真正的底层数据读写。

## 3. C 语言布尔玄学与内核编码规范

### ❓ 疑惑 6：为什么判错一会儿用 `if(ret)`，一会儿用 `if(!ret)`，一会儿又来个 `if(ret != 0)`？没有规范吗？
* **解析**：
    * **底层规则**：在 C 语言中，`0` 等于假（False），非 `0` 等于真（True）。`NULL` 指针也等于假。
    * **内核错误码铁律**：返回 `0` 代表成功；返回**负数**（如 `-EINVAL`）代表失败。
    * `if (ret)` = 如果有错误（因为非 0 为真）。
    * `if (!ret)` = 如果没有错误，一切顺利（因为 0 取反变真）。
    * `if (!指针)` = 如果指针为空（找不到数据或分配内存失败）。
    * **为什么会有 `ret != 0`？**：属于“祖传代码”的历史遗留问题。不同时代的开发者习惯不同。内核社区原则上**禁止单纯为了修改格式而提交 Patch (No Style-only Patches)**，以防弄乱 Git blame 历史和引发合并冲突。

## 4. 并发之巅：锁 (Mutex) 与 引用计数 (Refcount)

### ❓ 疑惑 7：大结局的 `nbd_put(nbd)` 是干嘛的？前面怎么没看到 `nbd_get`？
* **解析**：
    * 获取设备指针的函数（如 `nbd_find_get_unused` 或底层的 `refcount_inc_not_zero`）已经**暗中增加了引用计数**。这就相当于拿到了该内存块的“临时使用权”。
    * 用完必须还。但默认情况下，这个配置引用会被 `config` 继承，所以 `put_dev` 初始为 `false`。
    * 只有当用户要求特殊销毁逻辑（如 `DESTROY_ON_DISCONNECT`）导致引用计数多出 1 个时，才会设置 `put_dev = true`，并在函数末尾通过 `nbd_put(nbd)` 归还计数，防止内存泄漏。

### ❓ 疑惑 8：为什么要把 `mutex_unlock` 放在 `nbd_put` 前面？放后面不行吗？
* **解析（极其重要）**：
    * **绝对不行！会导致系统死机。**
    * 锁存在于 `nbd` 对象的内存中（`&nbd->config_lock`）。如果先执行 `nbd_put`，并且这是最后一个引用，内核会**立刻释放/炸毁 `nbd` 所在的整块内存**。
    * 此时如果再去执行 `mutex_unlock`，相当于访问野指针（Use-After-Free），触发 Kernel Panic。
    * **原则**：先交出操作权（开门/解锁），再交出存活权（拆楼/释放引用）。

### ❓ 疑惑 9：把锁解开后，在门外“裸奔”执行 `set_bit` 和 `refcount_inc`，不会引发并发问题吗？
* **解析**：
    * **自带防弹衣**：`set_bit` 和 `refcount_inc` 都是**硬件级别的原子操作（Atomic Operations）**。在 CPU 指令级别就锁死了总线，绝对不会发生数据撕裂，无需软件级别的 `mutex` 保护。
    * **收尾魔术（+1 又 -1）**：函数执行期间，手里始终握着初始化时给的 1 个保底引用计数。所以在门外无论怎么折腾，甚至别的线程抢到了锁来尝试销毁，引用计数都绝对跌不到 0。
    * **性能考量**：不需要锁保护的代码，就尽早挪到 `mutex_unlock` 之后执行。缩小临界区，能极大提升内核多核并发的吞吐量。
